# ADR 0006: Active probes plus passive ejection

Status: Accepted (Phase 0; passive reporting moved to the round trip and ejection made CAS-based in the Phase 2 fix round, see ADR 0009; ejection state kept across discovery flaps, see ADR 0010)

## Context

Backends crash, hang, get redeployed, or start returning errors while their process looks fine. The gateway has to stop sending traffic to a bad backend quickly, send traffic again once it recovers, and avoid flapping (rapid up/down/up) when a backend is borderline. The chaos test in Phase 8 measures failover time, so the detection speed must be explainable.

## Options considered

1. **Active checks only**: a goroutine per backend sends `GET <path>` every `interval`. It detects dead backends even with zero traffic, and it detects recovery. But detection takes roughly `interval × fall`, and a passing `/healthz` does not prove real requests succeed. Probe load grows with backends × gateways divided by `interval`.
2. **Passive checks only** (outlier detection on real traffic): it reacts within milliseconds when traffic is flowing, and it catches "healthz is OK but real endpoints return 500". But it needs traffic to detect anything, and it cannot tell when a backend has recovered, so it needs a timer.
3. **Rely on the platform** (Kubernetes readiness or Consul checks alone): no extra code. But it is slow (often 10 s or more), it does not exist for static upstreams, and it sees the backend from the platform's network position, not the gateway's.
4. **Both active and passive** (chosen), the same approach as Envoy and NGINX Plus.

## Decision

Both, as two independent signals that write **different fields** on `*balancer.Backend`, so they never need to coordinate:

```
Available(now) = !activeDown && now >= ejectedUntil
```

**Active (`health_check`)**: one goroutine per backend pointer, owned by `health.Checker` (whose `Run` is owned by `proxy.Gateway.Run`). It probes `GET base+path` with `timeout` (default `min(1s, interval/2)`; `Validate` requires `0 < timeout < interval`), and only a 2xx counts as success. Redirects are never followed (a 3xx is a failure), and probes carry no cookie jar. The default probe transport **ignores `HTTP_PROXY`/`HTTPS_PROXY`**: in a pod with an egress proxy configured, probes would otherwise go through a proxy that cannot reach in-cluster backends, and every backend would be marked down while real traffic works. Up and down use **hysteresis**: a backend goes down after `unhealthy_threshold` consecutive failures (fall, default 3) and comes back up after `healthy_threshold` consecutive successes (rise, default 2). The first probe of each backend is **jittered** within one `interval`, so probes do not arrive in sync. After that, the next probe is scheduled `interval` after the previous one **ended**, so probes of one backend **never overlap**, even when `timeout` is close to `interval`. New backends start **up** (the zero value of `activeDown` is false), because Consul has already vetted discovered instances, and starting them down would cause 503s for one interval after every reload. When `health_check` is omitted, active checking is off and `activeDown` stays false. When a probe is stopped because its upstream's `health_check` was **removed**, or because its target is gone, the Checker resets that backend's active health to **up** (`SetActiveHealthy(true)`). Without this, a backend that was down at the moment its check was removed would stay down forever, because nothing would ever probe it again. A probe that is merely *restarted* (its settings changed) keeps the current verdict, and the new probe corrects it within rise or fall probes. When a pointer's probe is replaced, the **successor always waits for its predecessor to exit** before it probes, and also before its own reset-to-up if it is stopped before it starts. Otherwise a predecessor's late "down" write could land after the reset and leave a removed backend down forever. The wait is bounded, because the predecessor is always canceled before its successor starts.

**Passive (`passive_health`)**: the proxy reports each attempt's outcome from a `RoundTripper` wrapper around the route's transport, where the outcome is actually known: the status at response-header time, or the transport error (ADR 0009). An error while copying the body after the headers have been sent is not reported. Reported as **failures**: any 5xx from the backend, transport errors (dial refused, reset, response-header timeout), and the gateway's own request deadline when the backend is the slow party (504). Anything else is a **success**. **Never reported**, neither as failure nor as success, because they say nothing about the backend: a request canceled by the client (499), a client body error (400), a stalled upload where the deadline fired while the gateway was still waiting for the client's body (408), and every request rejected before the balancer (bad path, CONNECT, bad Upgrade, 401, 404, 429). Without these rules, clients that hang up, send broken bodies or send requests the proxy refuses could eject healthy backends; the Phase 2 review did it with three `CONNECT` requests and zero backend hits (ADR 0009).

A success resets the backend's consecutive-failure streak. When the streak reaches `consecutive_failures` (default 5), the backend is ejected until `now + cooloff` (default 30 s) with `Backend.TryEject`, a compare-and-swap that succeeds only if the backend is **not already ejected** at `now`. So a burst of concurrent failures (requests that were in flight at the moment of ejection) produces exactly one ejection, one log line and one metric increment, and never extends a running cooloff. Re-admission is **lazy**: `Available` compares against the deadline, so no timer goroutine is needed. The streak is reset **only by a success**, not when the cooloff ends, and the threshold test is `streak >= N`. So a backend that comes back and fails again is re-ejected on its **first** failure: a natural half-open probe with no extra state.

**How they combine:** active is the authority on "is the process alive", and passive is a fast, short-lived circuit breaker on real traffic. Active recovery does not clear a passive ejection. The cooloff still runs, which is conservative and keeps the two signals independent. All of this state lives on the shared `*Backend`, so it survives config swaps (ADR 0002), and the passive part also survives a backend leaving and re-entering the live set within its 60 s grace period (ADR 0010; the probe is stopped and reset to up when it leaves). After each swap, `Checker.Sync(targets)` diffs targets by **`*Backend` pointer identity plus check settings**, not by backend ID. It starts probes for new pointers, stops probes for pointers that are gone, and restarts a probe whose settings changed. A backend that was pruned (after its grace period) and later re-added has the same ID but a **new** pointer from the Registry, so it gets a new probe. Diffing by ID would leave the new pointer unprobed and the old one probed forever. State transitions are reported through a callback, which feeds metrics and logs without the health package importing metrics. `tollgate_backend_up` means **in rotation** (`Available(now)`: active verdict up **and** not ejected), not just "probe passes".

**If every backend is unavailable** we return 503 (`ErrNoHealthyBackends`). We do not implement Envoy's "panic mode" (sending to all backends when too many are unhealthy) in v1.

## Consequences

- Good: under traffic, failover takes about as long as `consecutive_failures` requests, i.e. milliseconds. Without traffic it takes about `interval × fall` (15 s at the defaults). Both numbers are easy to state and to measure in Phase 8.
- Good: lock-free. Each signal does its own atomic writes and the balancer reads them.
- Cost: counting every 5xx as a failure means a single endpoint that keeps returning 500 can eject an otherwise healthy backend. The alternative (count only 502/503/504 and transport errors, like Envoy's "gateway failure" mode) is a small change in `ObservePassive` if this causes trouble. It is a separate question from *which attempts* are reported at all, which ADR 0009 settles.
- Cost: without panic mode, a bad health-check config, such as the wrong path, can mark everything down and cause a full outage. Validation and the upstream-health metric are the guards. Panic mode, or a cap on the percentage of backends that can be ejected, is future work.
- Cost: probe traffic grows with backends × gateway replicas.
