# ADR 0004: A hand-written token bucket per (route, client)

Status: Accepted (Phase 0; amended after the Phase 0 review, see architecture.md §11 items 10 and 18; amended again in the Phase 3 build and fix round: nanotoken arithmetic, seeded `maphash` sharding, three separate limiters, fail-closed failed-auth throttle at capacity)

## Context

Routes can set `rate_limit: {requests_per_second, burst}`. The limit applies per client. The client is the API key's client ID or the JWT client-ID claim. When the route has no auth, the client is the client IP, with IPv6 addresses masked to their /64 prefix (a single host usually controls a whole /64, so per-address keys would be trivially bypassed). A request over the limit gets `429 Too Many Requests` with a correct `Retry-After` header. The limiter runs on every request, so it must be O(1) and cheap. It must also use bounded memory even when there are millions of distinct clients, for example when IPs are spoofed, and running out of room must not become a way around the limit. The algorithm must be written from scratch.

## Options considered

1. **Fixed-window counter**: count requests per client per calendar second or minute. It is tiny and simple. But a client can send a full window's quota at 0:59 and another at 1:00, which is 2x the limit in a short burst. It also has no separate burst setting.
2. **Sliding-window log**: store a timestamp for every request in the window. It is exact, but memory per client is O(limit), which is unacceptable for high limits.
3. **Sliding-window counter**: a weighted mix of the current and previous fixed windows. It is O(1) and fairly smooth. But it is an approximation, it has no explicit burst setting, and the right `Retry-After` is awkward to compute.
4. **Token bucket**: each client has a bucket of up to `burst` tokens that refills at `rate` per second, and a request spends one token. It is O(1) with two numbers per client. Rate and burst map one-to-one onto our config, and `Retry-After` falls straight out of the arithmetic.
5. **GCRA**: one timestamp per client ("theoretical arrival time"). It is mathematically equivalent to a token bucket and uses even less memory, but it is harder to explain and to reason about.

There is a second, separate choice: **local versus global** state. A shared store like Redis gives an exact fleet-wide limit, but it adds a network hop to every request and a dependency that is not allowed.

## Decision

A **token bucket with lazy refill**, kept **locally in each gateway process** (`ratelimit.TokenBucket`). `Limiter.Allow(key, limit) Decision`, plus a read-only `Peek(key, limit) Decision` used by the failed-auth throttle below.

**Bucket state** is 24 bytes with no pointers (so the GC never scans bucket memory): `nanoTokens float64`, and `last`, `fullAt` as `time.Duration` **offsets from the limiter's start** (`now.Sub(epoch)`, which uses the monotonic clock). On `Allow` at offset `now`:

```
if now < last { now = last }               // clock behind (lock wait or injected clock): zero elapsed, never move last back
nanoTokens = min(burst*1e9, nanoTokens + float64(elapsed_ns)*rate)   // rate and burst of the limit passed to THIS call
last       = now
if nanoTokens >= 1e9 { nanoTokens -= 1e9; allowed }   // check-and-consume under the shard lock
else                 { retryAfter = ceil((1e9 - nanoTokens) / rate) ns, nudged up until the refill expression agrees }
fullAt     = now + time until nanoTokens reaches burst*1e9
```

- **Why nanotokens.** The first version counted whole tokens in float64. A refill was `elapsed.Seconds()*rate`, and 0.1 s is not exact in binary, so ten 100 ms refills at 1/s summed to `0.9999999999999999` and the token arrived one call late; with burst 1 the late surplus was then lost to the cap (a 60 s run admitted 55 instead of 61). In nanotokens a refill is `elapsed_ns × rate`, an exact integer for any rate with up to nine decimal places, so whole-token boundaries are exact and admissions do not drift. One shared `accrue` function (with an explicit `float64()` conversion, so arm64 cannot fuse it into an FMA that rounds differently) is used by both the refill and the `RetryAfter` computation.
- **`Peek`** runs the same arithmetic on a copy and returns the Decision `Allow` would return, without consuming, writing back or creating a bucket. An unknown key peeks as `Allowed` with `Remaining = burst`.
- **RetryAfter:** `Decision.RetryAfter` is the exact time until one whole token exists, **rounded up to the next nanosecond**, so "advance the clock by exactly RetryAfter, then Allow" always admits. The proxy rounds it **up** to whole seconds, minimum 1, for the `Retry-After` header. Rounding down would tell an obedient client to come back too early and earn a second 429. We also set `X-RateLimit-Limit` (burst) and `X-RateLimit-Remaining` (whole tokens left).
- **Key:** `route.Name + "\x00" + identity`. Each route has its own bucket per client. The NUL separator stops two different (route, client) pairs from producing the same string. The identity is the authenticated `ClientID`, or for `auth: none` routes the client-IP key: the IP from `RemoteAddr` with the port stripped, IPv4 unchanged, IPv4-mapped IPv6 (`::ffff:a.b.c.d`) un-mapped to IPv4 first, and other IPv6 masked to /64 (for example `2001:db8:1:2::/64`). Un-mapping must happen before masking, or every IPv4 client of a dual-stack listener would share one /64 bucket.
- **Limit is passed on every call**, so it is never stored as config. When a route's rate changes, the next request uses the new rate, and tokens are clamped to the new burst. The limiters live outside the config snapshot (ADR 0002), so buckets survive hot reloads.
- **Invalid limit fails open, and config cannot reach it.** A `Limit` with `RatePerSecond <= 0`, NaN, +Inf or `Burst < 1` returns `Allowed` and touches no bucket. `Validate` requires `0 < requests_per_second <= 1,000,000` and `1 <= burst <= 1,000,000`, and the snapshot builder rejects an invalid limit again, so this is a safety net, not a feature. The upper cap exists because a burst near `MaxInt` overflowed the nanotoken arithmetic (`X-RateLimit-Remaining: -9223372036854775808`); at `1e6 × 1e9 = 1e15` float64 is still exact (exact up to 2^53).
- **Limit changes and idle deletion (accepted bound).** `fullAt` is computed under the limit in force at the bucket's last `Allow`. The sweeper and the at-capacity eviction never see the route's *current* limit, so a key that is idle across a limit change can be deleted as "full" earlier than the new limit would say, and then recreated full at the new burst. We **accept and document** this bound: the over-admission is **less than one burst of the new limit, per key, once per limit change**, and limit changes are rare operator actions. The alternative (store the last-charged limit on each bucket and re-clamp when it differs) was rejected: `Allow` already clamps to the passed burst on every call, so the stored limit adds nothing on the `Allow` path, and it cannot close the gap, because deletion happens in the sweeper, which never sees the new limit.
- **Concurrency:** 32 shards, each a `sync.Mutex` and a `map[string]*bucket`, padded to 128 bytes so neighbouring locks do not share a cache line. The shard is chosen by `hash/maphash` with a **per-limiter random seed**. A fixed hash such as FNV-1a would let an attacker compute offline which keys land in one shard and fill that shard's `ceil(MaxKeys/32)` slots with 1/32 of the effort. A mutex, not atomics: the refill is a read-modify-write of three fields, and the map needs a lock anyway.
- **Memory bound: idle sweep.** A bucket that has been idle until `fullAt` is full again, which makes it identical to a brand-new bucket, so **deleting it is lossless** (subject to the limit-change bound above). `Run(ctx)` sweeps every `SweepInterval` (default 1 minute), locking one shard at a time, and returns **nil** when ctx is done.
- **Memory bound: hard cap, fail closed for new keys.** `MaxKeys` (default 100k) is enforced per shard as `ceil(MaxKeys/32)`, so the check needs no global counter. When a new key arrives at a full shard, the limiter looks at up to **8** existing buckets in map-iteration order (Go randomises the start) and evicts the first idle one (`now >= fullAt`), which loses nothing. If none is idle, the new key is **denied**: `Decision{Allowed: false, AtCapacity: true, RetryAfter: 1s}`, and the proxy answers 429 with `Retry-After: 1`. Buckets that still hold state (a throttled or partly drained client) are **never** evicted. The old "evict an arbitrary bucket" policy let an attacker who can mint keys (a /48 of IPv6 holds 65,536 /64s) wipe the throttled buckets of real clients, which is a bypass. The sample size bounds the work under the shard lock, so a key flood cannot become a CPU amplification.
- **Three limiters, three key budgets.** The `proxy.Gateway` creates and sweeps three `TokenBucket`s, each capped at `Options.LimiterMaxKeys` (default 100k): one for **authenticated identities** (api_key / jwt routes), one for **IP-keyed clients** (`auth: none` routes), and the **failed-auth throttle**. With one shared limiter, a flood of distinct IPs on a public route could fill the key table and deny new clients of authenticated routes with `AtCapacity`. Separate budgets confine a flood to its own class. Authenticated keys are bounded by valid client IDs × routes, so in practice only the IP-keyed limiter and the failed-auth throttle can reach their caps. An injected `Options.Limiter` replaces the first two (isolation is then the caller's concern).
- **Failed-auth throttle.** Credential guessing, and the CPU cost of RS256 verification, are limited per client-IP key (/64 for IPv6) with a fixed policy of **burst 10, refill 1 token per second**. On an `api_key` or `jwt` route the proxy first `Peek`s the client's failed-auth bucket. If it is empty, it answers 429 + `Retry-After` **without attempting verification**, even when the request carries valid credentials (a short lockout behind a brute-forcing IP or NAT, in exchange for a hard bound on guesses). Otherwise it authenticates. Only an `ErrInvalidCredentials` result charges the bucket (`Allow`); missing credentials cost no crypto and successes are never charged. **At capacity it fails closed for failures:** if the charge comes back `AtCapacity` (the throttle cannot track this IP), that failed attempt gets **429 instead of 401**. Answering 401 would let a client with fresh addresses guess unthrottled, and the 401-versus-success difference is exactly the oracle it wants; a 429 reveals nothing about the verification result. Valid credentials never reach that branch.
- **Peek-then-charge overshoot (accepted).** Peek and charge are not atomic, so N concurrent failures from one IP that all pass the Peek can all be verified. The overshoot is bounded by the concurrency **per refill wave**, not in total: each time a token refills, another wave can pass the Peek before the charges land (the Phase 3 review measured 10, 2, 2, 3, 3 verifications across waves of 500 concurrent failures).
- **Metrics:** denials are counted as `tollgate_ratelimited_total{route, reason}` with `reason` = `limit` (bucket empty) | `capacity` (`AtCapacity`) | `auth_throttle` (failed-auth throttle).
- **Clock injection:** `Options.Now` lets tests advance a fake clock instead of sleeping, so limiter tests are exact and fast.

## Consequences

- Good: O(1) time and 24 bytes of bucket state (plus the map entry and key) per active client, with idle clients cleaned up for free. Rate and burst are what operators already understand. A parallel benchmark ran at about 190 ns/op with 0 allocations.
- Good: correct and exact `Retry-After`, no long-run drift, and fully deterministic tests.
- Good: neither a key flood nor a limit change can reset a throttled client's bucket, and an anonymous flood cannot lock out authenticated clients. The only over-admission paths are bounded and documented (one burst per key per limit change, and the per-wave overshoot of the failed-auth throttle).
- Cost: **limits are per gateway replica.** Behind R replicas, a client can get up to R × rate if the external load balancer spreads its requests. Mitigations, in order of cost: document it; configure `rate / R`; later, a global limiter (Redis plus GCRA) or "local with periodic sync".
- Cost: at `MaxKeys` a limiter **fails closed for new identities** (429) until idle buckets free up. We accept this in exchange for bounded memory and for never handing out a fresh bucket to someone who was being throttled. It is alertable through `reason="capacity"`.
- Cost: a /64 key groups every device on one IPv6 subnet, and an IPv4 NAT groups every client behind it. Both share one bucket on `auth: none` routes and one failed-auth budget. `trusted_proxies` / X-Forwarded-For handling is future work (architecture.md §10).
- Cost: three limiters means three sweeper goroutines and three key budgets to size. `LimiterMaxKeys` applies to each, so worst-case bucket memory is three times one budget.
